# Выбор и настройка мониторинга в системе

## Анализ системы

Три приложения (Shop, CRM, MES), две PostgreSQL, S3, RabbitMQ между CRM и MES. По одному EC2 на сервис — узкие места по ресурсам.

**Яндекс Метрика** видит только B2C-сайт. B2B-заказы идут через MES API → RabbitMQ → CRM, без визита на сайт. Слепая зона: очереди, ошибки API, застрявшие заказы между системами.

| Зона | Что мониторить в первую очередь |
|------|--------------------------------|
| B2C | Shop API, Shop DB, S3 |
| CRM | CRM API, RabbitMQ (publish) |
| MES + B2B | MES API, MES DB, очередь расчёта цен |
| Интеграция | RabbitMQ DLQ, глубина очереди |
| Инфра | CPU/RAM EC2, connections БД |


## Мотивация

**Зачем:** жалобы на просрочку при нормальном производстве, потеря B2B-контрактов, медленный дашборд MES. Причины неизвестны — расследование вручную занимает дни.

**Что даст:**
- Найти застрявший заказ за минуты, а не недели
- Видеть перегрузку MES/B2B до звонков клиентов
- Обосновать масштабирование данными, а не ощущениями

**Для бизнеса:** 2–3 спринта на мониторинг дешевле одного потерянного B2B-контракта.


## Выбор подхода к мониторингу

| Часть системы | Подход | Почему |
|---------------|--------|--------|
| Shop / CRM / MES API | **RED** | Rate, Errors, Duration — базовый SLA HTTP-сервисов |
| EC2, PostgreSQL, RabbitMQ | **USE** | Utilization, Saturation, Errors — ресурсы с лимитом |
| Pipeline заказа (бизнес) | **4 золотых сигнала** | Сквозной путь, который RED/USE по отдельности не видят |
| S3 | USE (упрощённо) | Рост объёма = планирование ёмкости |


## Метрики

### Выбранные метрики

| Метрика | Где | Зачем | Ярлыки |
|---------|-----|-------|--------|
| DLQ letters (RabbitMQ) | Интеграция | Потерянные сообщения = потерянные заказы | `queue_name`, `source_service` |
| Messages in flight (RabbitMQ) | Интеграция | Глубина очереди, «завал» после B2B API | `queue_name` |
| RPS (Shop / CRM / MES API) | API | Трафик, аномалии, рост нагрузки | `method`, `endpoint`, `status_code` |
| RPS per user (MES API) | MES | «Шумный» B2B-партнёр | `api_client_id`, `client_type` |
| Latency (Shop / CRM / MES API) | API | RED Duration; для MES — дашборд и расчёт цены | `endpoint`, `percentile`, `client_type` |
| HTTP 500 (Shop / CRM / MES API) | API | RED Errors | `endpoint`, `client_type` |
| CPU % (все API) | EC2 | USE Utilization, пора scale-up | `instance_id`, `service` |
| Memory % (все API) | EC2 | Риск OOM | `instance_id`, `service` |
| Memory % (Shop DB / MES DB) | БД | Падение cache → рост latency | `db_name` |
| Connections (Shop DB / MES DB) | БД | USE Saturation, исчерпание пула | `db_name`, `state` |
| Size (Shop DB / MES DB / S3) | Хранилище | Планирование ёмкости | `db_name` / `bucket` |

### Не выбраны

| Метрика | Почему |
|---------|--------|
| RPS per user (Shop, CRM) | Мало пользователей, хватает общего RPS |
| HTTP 200 | Дублирует RPS |
| Simultaneous sessions | Для stateless API заменяется RPS + connections |
| Kb transferred | Низкий приоритет; добавить на этапе 2 |

### Дополнительно (не из списка)

| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| `orders_stuck_count` | Заказы без смены статуса > 48 ч — главная бизнес-метрика | `status`, `channel` |
| `order_stage_duration` | Время этапа pipeline | `from_status`, `to_status` |
| `price_calc_queue_depth` | Очередь расчёта цен (2–30 мин) | `priority` |


## Показатели насыщенности

| Ресурс | Warning | Critical | При превышении |
|--------|---------|----------|----------------|
| CPU API | > 70% / 10 мин | > 85% / 5 мин | Slack → scale-up MES EC2 |
| Memory API | > 75% | > 90% | Slack → рестарт / scale-up |
| DB connections | > 70% max | > 85% max | Алерт DevOps → kill idle, read replica |
| RabbitMQ in flight | > 500 | > 2000 | Увеличить consumers, приоритет B2C |
| RabbitMQ DLQ | ≥ 1 | ≥ 10 | **PagerDuty** → support, ручной reprocess |
| MES latency p95 (дашборд) | > 2 с | > 5 с | Инцидент → оптимизация запросов |
| MES latency p95 (расчёт) | > 5 мин | > 15 мин | Throttle B2B, уведомить партнёров |
| `orders_stuck_count` | ≥ 5 | ≥ 20 | Алерт PM + support → связь с клиентами |

**Эскалация:** Warning → Slack `#alerts`. Critical → PagerDuty + Jira INCIDENT (15 мин). DLQ и stuck orders — 24/7.


## План действий

Оценка: **3–4 спринта** (DevOps full-time + 2 backend по 50%).

| Этап | Задачи |
|------|--------|
| **1. Инфра** | VictoriaMetrics/Yandex Monitoring + Grafana + Alertmanager; exporters (node, postgres, rabbitmq) |
| **2. API** | OpenTelemetry в Shop/CRM/MES; RED-метрики; `correlation_id` в логах |
| **3. Бизнес** | `orders_stuck_count`, `order_stage_duration`, `price_calc_queue_depth`; алерты DLQ |
| **4. Дашборды** | Обзор системы, pipeline заказа, B2B API, инфраструктура; runbook'и |
| **5. Процессы** | Дежурство, Jira-интеграция, обучение support |

Приоритет внедрения: **MES API → RabbitMQ → бизнес-метрики заказа**.
