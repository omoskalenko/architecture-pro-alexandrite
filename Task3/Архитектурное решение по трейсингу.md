# Архитектурное решение по трейсингу

## Анализ: где заказ может зависнуть

Заказ проходит 3 системы и RabbitMQ. Трейсинг нужен **на каждом переходе** — именно на границах сервисов теряются сообщения и время.

| # | Точка | Риск | Покрытие трейсингом |
|---|-------|------|---------------------|
| 1 | Shop API: создание заказа, загрузка 3D | Ошибка записи в Shop DB / S3 | Shop API, Shop DB span |
| 2 | CRM API: подтверждение производства | Заказ не уходит в MES | CRM API span |
| 3 | CRM API → RabbitMQ (publish) | Сообщение не опубликовано | Span publish + `message_id` |
| 4 | RabbitMQ → MES API (consume) | **Потеря / задержка сообщения** | Span consume, propagation через headers |
| 5 | MES API: расчёт цены (2–30 мин) | Долгий / упавший расчёт | Child span `calculate-price` |
| 6 | B2B: MES API → RabbitMQ → CRM API | Обратный поток, двойная точка отказа | Сквозной trace B2B |
| 7 | MES API: дашборд операторов | Медленный ответ → заказ не взят | Span `GET /orders` |
| 8 | MES DB / Shop DB | Рассинхрон статусов | DB spans (опционально) |

**Покрыть трейсингом:** Shop API, CRM API, MES API, RabbitMQ (propagation), S3-операции в API. Фронтенды — передача `traceparent` в API-запросах.

Диаграмма с новыми компонентами (красным): [jewerly_c4_model_tracing.drawio](./jewerly_c4_model_tracing.drawio)


## Данные в трейсе

| Поле | Назначение |
|------|-----------|
| `trace_id` | Сквозной идентификатор цепочки |
| `span_id`, `parent_span_id` | Иерархия вызовов |
| `order_id` | **Бизнес-ключ** — поиск «что было с заказом X» |
| `message_id` | Связь с сообщением RabbitMQ |
| `from_status`, `to_status` | Переход статуса |
| `channel` | `b2c` / `b2b` |
| `api_client_id` | B2B-партнёр |
| `service.name` | shop-api / crm-api / mes-api |
| `operation` | HTTP method + path или `rmq.publish` / `rmq.consume` |
| `error`, `exception.message` | Ошибки |
| `duration_ms` | Длительность span |
| `user_id` (хэш) | Для аудита, без PII в открытом виде |

Propagation: заголовок **W3C `traceparent`** в HTTP; те же поля — в headers сообщений RabbitMQ.


## Мотивация

**Зачем:** заказы зависают между системами, сообщения теряются. Сейчас support не видит, где заказ «застрял» — расследование занимает дни.

**Что даст:**
- Поиск по `order_id` → полная цепочка за секунды
- Видно, на каком span оборвался trace (потеря в RabbitMQ vs падение MES)
- Данные для оптимизации (расчёт цены 30 мин, медленный дашборд)

**Метрики, на которые повлияет трейсинг:**

| Метрика | Тип | Эффект |
|---------|-----|--------|
| MTTR инцидента с заказом | Бизнес | Дни → минуты |
| `orders_stuck_count` | Бизнес | Снижение за счёт раннего обнаружения |
| `order_stage_duration` | Техн. | Измеряется из span-ов |
| p95 latency MES API | Техн. | Находим медленные spans |
| % traces с разрывом в RabbitMQ | Техн. | Индикатор потери сообщений |


## Предлагаемое решение

### Стек

| Компонент | Технология | Роль |
|-----------|-----------|------|
| Инструментирование | OpenTelemetry SDK (Java, .NET) | Spans в Shop / CRM / MES API |
| Сбор | OpenTelemetry Collector | Приём, фильтрация, экспорт |
| Хранение | Grafana Tempo | Хранение и поиск трейсов |
| Просмотр | Grafana | UI: поиск по `order_id`, timeline заказа |
| Логи | Yandex Cloud Logging + `trace_id` | Корреляция логов и трейсов |

### Доработки в существующих сервисах

1. **Shop API, CRM API** — OTel Spring Boot starter, middleware для `traceparent`, span на смену статуса.
2. **MES API** — OTel .NET, spans на `/orders`, `/calculate-price`, consume/publish RabbitMQ.
3. **RabbitMQ** — при publish копировать `traceparent` в AMQP headers; при consume — продолжать trace.
4. **Фронтенды** — генерировать `traceparent` на действие пользователя, передавать в API.

### Новые компоненты (красные на схеме)

- **OpenTelemetry Collector** — все API шлют spans по OTLP
- **Trace Storage (Tempo)** — персистентное хранение
- **Grafana** — дашборд «История заказа»

Схема: [jewerly_c4_model_tracing.drawio](./jewerly_c4_model_tracing.drawio)

### Мониторинг и алертинг (доп. задание)

На основе трейсов — **Order Pipeline Monitor** (периодический job):

1. Ищет заказы без нового span > 48 ч или trace с разрывом после RabbitMQ.
2. Пишет метрику `orders_stuck_count` в Prometheus.
3. При пороге — Alertmanager → Slack / PagerDuty.

Дополнительно: OTel Collector экспортирует **span metrics** (duration, error rate) в Prometheus.

Новые компоненты (зелёные): Order Pipeline Monitor, Prometheus, Alertmanager.

Схема: [jewerly_c4_model_tracing_monitoring.drawio](./jewerly_c4_model_tracing_monitoring.drawio)


## Компромиссы

| Ситуация | Почему трейсинг не поможет / дорого |
|----------|-------------------------------------|
| Проблема **вне IT** (логистика, цех) | Trace обрывается на SHIPPED; нужны данные от транспортной компании |
| **S3 / Managed DB** | Глубокий трейсинг внутри Yandex Cloud ограничен; только spans на уровне SDK-клиента |
| **100% покрытие** при +100 заказов/мес | Хранить все traces дорого → sampling: 100% ошибок, 10% успешных B2C, 100% B2B |
| Старый код без рефакторинга | Полная автоматическая инструментизация .NET/Java покрывает HTTP, но не все внутренние методы |
| Фронтенд Three.js | Трейсинг 3D-редактора в браузере — низкий приоритет, достаточно trace на upload API |


## Безопасность

| Угроза | Мера |
|--------|------|
| Утечка PII в spans | Не логировать ФИО, телефон, адрес; `user_id` — хэш; маскирование в Collector |
| Доступ к трейсам | Grafana: SSO компании, роли `Support` (read), `Engineer` (read), `Admin` |
| Внешний доступ | Трейсинг **только внутри** VPN / private network; Tempo без публичного endpoint |
| B2B API User | В trace только `api_client_id`, не детали чужих заказов; фильтр по tenant в Grafana |
| Хранение | Retention 30 дней; после — удаление (GDPR / персональные данные в заказах) |
| RabbitMQ headers | Только `trace_id` / `order_id`, без тела заказа |
