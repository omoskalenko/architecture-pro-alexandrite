# Планирование: анализ, идентификация проблем и поиск решений

## Контекст

Компания «Александрит» — производство ювелирных изделий (B2C онлайн-магазин + B2B API). Три приложения: онлайн-магазин (Vue + Spring Boot), CRM (Vue + Spring Boot), MES (React + C#). Интеграция CRM ↔ MES через RabbitMQ. Инфраструктура в Yandex Cloud: по одному EC2-инстансу на приложение, PostgreSQL (один инстанс на чтение и запись), S3 для 3D-файлов.

Основные симптомы: просроченные заказы при достаточных производственных мощностях, медленный дашборд MES, потеря B2B-контрактов после открытия API, рост нагрузки ~+100 заказов/месяц.

## 1. Список проблемных мест

### 1.1. Производительность и масштабируемость

| # | Проблема | Тип | Обоснование |
|---|----------|-----|-------------|
| P1 | Медленная загрузка дашборда MES | Существующая | Операторы жалуются на долгую прогрузку первой страницы. Фильтр по статусам и пагинация не помогли — вероятны неоптимальные запросы, отсутствие индексов под сортировку «самые новые», тяжёлые JOIN-ы, отсутствие кэширования. |
| P2 | Расчёт стоимости блокирует поток заказов | Существующая | Расчёт в MES занимает 2–30 минут в зависимости от сложности 3D-модели. При росте заказов и B2B API очередь расчётов растёт быстрее, чем пропускная способность. |
| P3 | Отсутствие горизонтального масштабирования | Существующая | По одному EC2 на каждое приложение, одна БД на чтение и запись. Нельзя независимо масштабировать расчёт цен, API и дашборд операторов. |
| P4 | Единая БД MES на чтение и запись | Существующая | Дашборд (тяжёлые SELECT) конкурирует с записью статусов и расчётом цен на одном инстансе PostgreSQL. |
| P5 | Нагрузка от B2B API на MES API | Существующая | Внешние пользователи API обращаются напрямую в MES API без видимого rate limiting, очередей приоритетов и SLA. После открытия API систему «завалило» заказами. |

### 1.2. Интеграция и согласованность данных

| # | Проблема | Тип | Обоснование |
|---|----------|-----|-------------|
| P6 | Разделённые хранилища заказов (Shop DB и MES DB) | Существующая | Данные заказа размазаны между Shop DB (клиент, корзина, SUBMITTED) и MES DB (производственные статусы). Синхронизация только через RabbitMQ — риск рассинхронизации. |
| P7 | CRM API имеет прямой доступ к Shop DB | Существующая | На схеме CRM API читает/пишет Shop DB напрямую. Тесная связность, сложно эволюционировать схему, высокий риск неконсистентных изменений. |
| P8 | Ненадёжность асинхронной интеграции через RabbitMQ | Существующая / потенциальная | Нет упоминания DLQ, retry-политик, идемпотентности обработчиков, паттерна Outbox. При сбоях сообщения могут теряться или дублироваться — заказ «застревает» между системами. |
| P9 | Нестандартный B2B-поток: заказ создаётся в CRM по сообщению от MES | Существующая | Для B2B: MES считает цену → сообщение в очередь → CRM создаёт заказ. Обратный порядок относительно B2C, увеличивает задержку и точки отказа. |
| P10 | Отсутствие единого источника правды по статусу заказа | Существующая | Статусы меняются в трёх системах (магазин, CRM, MES). Нет единого представления «где сейчас заказ» для поддержки и клиентов. |

### 1.3. Наблюдаемость и операционная готовность

| # | Проблема | Тип | Обоснование |
|---|----------|-----|-------------|
| P11 | Отсутствие сквозной трассировки заказа | Существующая | При жалобах «заказ в работе несколько месяцев» невозможно быстро определить, в какой системе и на каком этапе он застрял. |
| P12 | Нет метрик и алертов по SLA | Потенциальная | Нет данных о времени прохождения этапов, размере очередей RabbitMQ, длине очереди расчёта цен, p95 загрузки дашборда. |
| P13 | Нет дашборда для бизнеса по просроченным заказам | Потенциальная | Продавцы и менеджеры узнают о проблемах от клиентов, а не из системы. |

### 1.4. Процессы разработки и релизов

| # | Проблема | Тип | Обоснование |
|---|----------|-----|-------------|
| P14 | Ручной деплой в prod/release | Существующая | Замедляет доставку исправлений. При критических инцидентах время реакции выше. |
| P15 | QA-узкое горло | Существующая | Один QA, ручные E2E. High/highest баги блокируют релиз. Задержки релизов растут. |
| P16 | Недостаток автоматизированных тестов интеграции | Потенциальная | Интеграция CRM ↔ MES через RabbitMQ — зона повышенного риска, но автотестов мало (QA только прототипирует). |

### 1.5. Архитектурные риски на перспективу

| # | Проблема | Тип | Обоснование |
|---|----------|-----|-------------|
| P17 | 3D-файлы: нет выделенного pipeline обработки | Потенциальная | MES тянет файлы из S3 для расчёта. При росте объёма нет отдельного воркер-пула, приоритизации, контроля размера/полигонов на входе. |
| P18 | Отсутствие API Gateway | Потенциальная | B2B API открыт напрямую на MES API — нет централизованной аутентификации партнёров, throttling, версионирования. |
| P19 | Нет механизма уведомления B2B-клиентов | Существующая | API-пользователи «не получили заказы» — вероятно, нет webhook/callback о смене статуса, только polling или ручной контакт. |
| P20 | Отказоустойчивость RabbitMQ | Потенциальная | Один инстанс очереди — SPOF для всей интеграции CRM ↔ MES. |

## 2. Инициативы по устранению проблем

| # | Инициатива | Закрывает проблемы | Оценка усилий |
|---|-----------|-------------------|---------------|
| I1 | **Сквозная observability**: correlation ID на заказ, distributed tracing (OpenTelemetry), централизованные логи, дашборд «застрявших» заказов | P10, P11, P12, P13 | M (2–4 нед.) |
| I2 | **Оптимизация дашборда MES**: анализ slow queries, индексы под `(status, created_at DESC)`, денормализованная проекция для списка заказов, кэш Redis для горячих статусов | P1, P4 | S–M (1–3 нед.) |
| I3 | **Read replica для MES DB** + маршрутизация чтений дашборда на реплику | P1, P4, P3 | S (1–2 нед., DevOps) |
| I4 | **Выделенная очередь расчёта цен** с воркерами (отдельные инстансы/процессы), приоритеты B2C > B2B, лимит параллельных расчётов | P2, P5, P17 | M (3–5 нед.) |
| I5 | **Надёжность RabbitMQ**: Outbox pattern в CRM и MES, DLQ, retry с exponential backoff, идемпотентные consumer-ы, мониторинг глубины очередей | P8, P20 | M (3–4 нед.) |
| I6 | **API Gateway** перед MES API: rate limiting per partner, квоты, версионирование, async response (202 + callback URL) | P5, P18, P19 | M (3–4 нед.) |
| I7 | **Webhook-уведомления для B2B**: при смене статуса — push в endpoint партнёра с retry | P19 | S (1–2 нед.) |
| I8 | **Единый Order Status API / read model**: материализованное представление статуса заказа (CQRS), обновляется из событий всех систем | P6, P10, P13 | L (6–8 нед.) |
| I9 | **Рефакторинг доступа CRM к Shop DB**: CRM работает через Shop API, убрать прямой доступ к БД | P7 | M (3–4 нед.) |
| I10 | **Автоматизация CI/CD prod**: blue-green или rolling deploy, smoke-тесты после деплоя | P14 | S (1–2 нед., DevOps) |
| I11 | **Интеграционные тесты RabbitMQ** в CI (Testcontainers) | P16 | S (2 нед., QA + backend) |
| I12 | **Горизонтальное масштабирование MES API** (2+ инстанса за load balancer) | P3, P5 | S (1–2 нед., DevOps) |
| I13 | **Валидация 3D-моделей на входе**: лимит полигонов, предупреждение клиенту, отклонение экстремально тяжёлых моделей | P2, P17 | S (1–2 нед.) |
| I14 | **Уведомления B2C-клиентам** о статусе заказа (email/push/личный кабинет) | P10, P13 | M (2–3 нед.) |
| I15 | **Найм**: +1 backend (Java/C#), +1 DevOps или SRE-функции на 50% FTE для observability и инфраструктуры | Все | — |

## 3. Приоритизация инициатив

### Логика приоритизации

Использую матрицу **Impact × Urgency / Effort** с учётом ограничений команды (8 инженеров, 2-недельные спринты, активный кризис с заказами).

**Принципы:**

1. Сначала — **видимость** (где застревают заказы) и **быстрые wins** по дашборду MES — это ежедневная боль операторов и источник пропущенных заказов.
2. Затем — **стабилизация потока** (очередь расчёта, надёжность RabbitMQ, API throttling) — корневая причина роста просрочек после открытия API.
3. Параллельно — **инфраструктурные quick wins** (read replica, 2-й инстанс MES) силами DevOps.
4. Структурные изменения (единый Order Status, рефакторинг CRM→Shop DB) — после стабилизации, в течение 6 месяцев.

| **P0** | I2 Оптимизация запросов дашборда MES | 1–3 нед. | Операторы не видят новые заказы вовремя → заказы «пропадают» с точки зрения производства. Прямая связь с мотивацией операторов. |

## 4. Целевая архитектура через полгода

### Ключевые изменения относительно текущей архитектуры

1. **API Gateway** — единая точка входа для B2B, rate limiting, async API (202 + webhook).
2. **Price Calc Workers** — расчёт цен вынесен из синхронного пути MES API в отдельную очередь с контролируемым параллелизмом.
3. **MES DB: primary + read replica** — дашборд читает с реплики, расчёты и записи — с primary.
4. **MES API за load balancer** — 2+ инстанса, горизонтальное масштабирование.
5. **RabbitMQ с Outbox + DLQ** — гарантированная доставка событий между CRM и MES.
6. **Observability** — correlation ID сквозь все системы, алерты на заказы без движения > N часов.
7. **Order Status Service (read model)** — единое место для ответа «где мой заказ» (CRM, B2B webhook, личный кабинет).
8. **CRM API больше не ходит напрямую в Shop DB** — только через Shop API (этап 2, если не успеем — в плане на следующие 6 месяцев).

## 5. Топ-3 инициативы, если можно сделать только три

### Выбор: I1 + I2/I3 + I4

| # | Инициатива | Почему именно она |
|---|-----------|-------------------|
| **1** | **I1 — Observability и дашборд застрявших заказов** | Компания теряет контракты, но **не знает, где именно ломается цепочка**. Это «рентген»: без него остальные изменения невозможно валидировать. Correlation ID + трейсинг + алерт «заказ без смены статуса > 48 ч» дают немедленную пользу поддержке и позволяют приоритизировать дальнейшие фиксы на данных, а не на догадках. Усилия умеренные, C# и Java разработчики могут внедрить за 2–3 спринта. |
| **2** | **I2 + I3 — Оптимизация дашборда MES + read replica** | Считаю это одной инициативой: **операторы — узкое горлышко производства**. Производственные мощности есть в 2× запасе, но операторы физически не успевают забирать заказы из-за медленного UI. Кто первый увидел — тот получил оплату; медленный дашборд = невзятые в работу заказы = «заказ несколько месяцев в работе» с точки зрения клиента. Индексы + оптимизация запросов + реплика — быстрый и измеримый эффект (p95 загрузки страницы). |
| **3** | **I4 — Очередь расчёта цен с выделенными воркерами** | После открытия B2B API расчёт цен стал **главным потребителем ресурсов MES**. Синхронный/полусинхронный расчёт (2–30 мин) при линейном росте заказов создаёт очередь, которая задерживает весь pipeline: SUBMITTED → PRICE_CALCULATED → MANUFACTURING_APPROVED. Выделение воркеров с лимитом параллелизма и приоритетом B2C стабилизирует систему без полного рефакторинга. Это адресует корневую причину деградации после API. |

### Почему не I5 (RabbitMQ) и I6 (API Gateway) в топ-3

- **I5 (надёжность RabbitMQ)** критична, но без I1 мы не знаем, теряются ли сообщения или заказы застревают на другом этапе. I1 должна предшествовать или идти параллельно; при выборе только трёх — observability важнее, потому что определяет, нужен ли вообще I5 в таком объёме.
- **I6 (API Gateway)** защищает от повторного завала, но **текущий завал уже произошёл** — сейчас важнее разгрузить обработку (I4) и ускорить потребление заказов операторами (I2/I3). Gateway можно добавить 4-й очередью в спринте 3–4.

### Ожидаемый результат через 6 месяцев при выполнении топ-3 + P1-инициатив

- Время обнаружения «застрявшего» заказа: с дней/недель → **< 1 часа** (алерт).
- p95 загрузки дашборда MES: с «неприемлемо» → **< 2 сек**.
- Очередь расчёта цен: **управляемая**, с видимым ETA и приоритетами.
- Жалобы на просрочку: снижение за счёт того, что заказы перестают теряться между «посчитано» и «взято в работу».
