# Архитектурное решение по логированию

## Анализ: откуда собирать логи

| Система | Сбор логов | Приоритет | Почему |
|---------|-----------|-----------|--------|
| **MES API** | Да | P0 | B2B API, расчёт цен, дашборд — главный источник инцидентов |
| **CRM API** | Да | P0 | Подтверждение заказа, publish/consume RabbitMQ |
| **RabbitMQ** | Да | P0 | Потеря сообщений — ключевая гипотеза по «зависшим» заказам |
| **Shop API** | Да | P1 | B2C-заказы, загрузка 3D |
| **Shop / CRM / MES (frontend)** | Частично | P2 | Ошибки UI; основное — на API |
| **Shop DB / MES DB** | Audit/slow query | P3 | Managed PostgreSQL — логи провайдера, не приложения |
| **S3** | Access logs | P3 | Планирование ёмкости, не разбор заказов |

Формат везде: **structured JSON** с полями `timestamp`, `level`, `service`, `order_id`, `trace_id`, `message`, `context`.

Схема: [jewerly_c4_model_logging.drawio](./jewerly_c4_model_logging.drawio) — красным отмечены источники логов и новые компоненты.


## Логи уровня INFO

| Событие | Система | Поля в логе |
|---------|---------|-------------|
| Создание заказа | Shop API | `order_id`, `customer_id` (hash), `channel=b2c`, `status=INITIATED` |
| Загрузка 3D-файла | Shop API | `order_id`, `file_id`, `file_size_mb`, `s3_key` |
| Смена статуса заказа | Shop / CRM / MES API | `order_id`, `from_status`, `to_status`, `actor` (user/operator/system) |
| Подтверждение производства | CRM API | `order_id`, `seller_id`, `status=MANUFACTURING_APPROVED` |
| Публикация в RabbitMQ | CRM / MES API | `order_id`, `queue`, `message_id`, `event_type` |
| Получение из RabbitMQ | CRM / MES API | `order_id`, `queue`, `message_id`, `delivery_tag` |
| Старт / завершение расчёта цены | MES API | `order_id`, `duration_ms`, `polygon_count`, `api_client_id` |
| B2B-запрос расчёта | MES API | `order_id`, `api_client_id`, `request_id` |
| Оператор взял заказ | MES API | `order_id`, `operator_id`, `status=MANUFACTURING_STARTED` |
| HTTP-запрос (summary) | Все API | `method`, `path`, `status_code`, `duration_ms`, `order_id` |

### Другие уровни

| Уровень | Когда |
|---------|-------|
| **ERROR** | 500, необработанное исключение, ошибка БД/S3, сообщение в DLQ, сбой расчёта цены |
| **WARN** | Retry RabbitMQ, медленный запрос (> порога), отклонённая 3D-модель, 4xx от B2B |
| **DEBUG** | Только dev/stage; детали SQL, payload сообщений (без PII) |
| **FATAL** | Падение процесса, OOM — немедленный алерт |

INFO — штатный поток заказа. ERROR/WARN — для алертов и разбора инцидентов. DEBUG не включать в prod.


## Мотивация

**Зачем:** сейчас support узнаёт о проблеме от клиента, разработчики ищут причину часами по разрозненным логам на EC2 (если они вообще есть).

**Что даст:**
- Поиск по `order_id` → все события заказа в одном месте
- Корреляция с трейсами через `trace_id`
- Меньше эскалаций в разработку

**Метрики:**

| Метрика | Тип | Эффект |
|---------|-----|--------|
| MTTR разбора инцидента | Бизнес | Часы → 15–30 мин |
| Обращений в support «где заказ» | Бизнес | Снижение — support сам смотрит логи |
| % инцидентов без root cause | Техн. | Снижение |
| Время поиска лога по order_id | Техн. | < 1 мин |
| ERROR rate по сервисам | Техн. | Видимость до жалоб клиентов |


## Приоритет: логирование vs трейсинг

Команда не потянет всё сразу. Общий принцип: **сначала критический путь заказа CRM ↔ RabbitMQ ↔ MES**.

| Очередь | Система | Логирование | Трейсинг | Почему |
|---------|---------|-------------|----------|--------|
| **1** | MES API | ✓ | ✓ | B2B, расчёт цен, дашборд — максимум жалоб |
| **1** | CRM API | ✓ | ✓ | Подтверждение и интеграция с MES |
| **1** | RabbitMQ | ✓ (server logs) | ✓ (propagation) | Потеря сообщений |
| **2** | Shop API | ✓ | ✓ | B2C; частично закрыт Метрикой |
| **3** | Frontends | ✓ (errors) | — | Низкий ROI |
| **3** | DB / S3 | audit | spans опционально | Managed-сервисы |

**Логирование чуть раньше трейсинга** в MES/CRM: structured JSON с `order_id` внедрить за 1 спринт; полный distributed tracing — за 2. Логи дадут пользу до готовности Tempo.


## Предлагаемое решение

### Стек

| Компонент | Технология | Роль |
|-----------|-----------|------|
| Формат | JSON (Logback / Serilog) | Structured logs в приложениях |
| Агент | Fluent Bit на EC2 | Сбор stdout + файлов → forward |
| Pipeline | OpenTelemetry Collector (logs) | Парсинг, маскирование PII, маршрутизация |
| Хранение | **Grafana Loki** | Индексация по labels, не по full-text |
| Поиск | Grafana | `{service="mes-api"} \| json \| order_id="123"` |
| Алерты | Loki → Alertmanager / Grafana Alerting | ERROR spike, аномалии |

### Новые компоненты (красные на схеме)

- **Fluent Bit** — на каждом EC2
- **OTel Collector (logs)** — маскирование, batch
- **Loki** — хранилище
- **Grafana** — UI (общий с трейсингом из Task3)

Схема: [jewerly_c4_model_logging.drawio](./jewerly_c4_model_logging.drawio)

### Доработки в сервисах

- MDC / scoped logging: `order_id`, `trace_id` во всех log statements
- Единый JSON-формат для Java (Logstash encoder) и C# (Serilog)
- RabbitMQ: лог publish/consume с `message_id`
- Корреляция: клик из Grafana Logs → trace в Tempo по `trace_id`


## Безопасность

| Аспект | Политика |
|--------|----------|
| PII | Не логировать ФИО, телефон, email, адрес. `customer_id` — hash |
| Маскирование | OTel Collector: regex-фильтр перед записью в Loki |
| Доступ | Grafana SSO; роли: `Support` (read prod), `Engineer` (read all), `Admin` |
| B2B | Support видит только `api_client_id`, не данные других партнёров |
| Сеть | Loki в private subnet, без публичного API |
| Аудит | Логировать факт доступа к поиску по order_id (кто, когда) |


## Хранение

| Индекс (Loki label) | Retention | Оценка объёма | Обоснование |
|---------------------|-----------|---------------|-------------|
| `service=mes-api` | 30 дней | ~5 GB/мес | Самый шумный; B2B + расчёт цен |
| `service=crm-api` | 30 дней | ~2 GB/мес | Меньше RPS |
| `service=shop-api` | 14 дней | ~3 GB/мес | B2C, дублирует часть Метрики |
| `service=rabbitmq` | 14 дней | ~1 GB/мес | Server logs |
| ERROR/WARN (all) | 90 дней | +20% | Дольше для расследований |

**Итого:** ~10–15 GB/мес hot storage. Старые ERROR — S3 cold archive (опционально).

Отдельный **tenant/label на сервис**, не отдельный кластер — достаточно для команды из 8 человек.


## От сборa к анализу

### Алертинг

| Алерт | Условие | Действие |
|-------|---------|----------|
| ERROR spike | > 10 ERROR/мин на MES API | Slack → DevOps |
| DLQ event | Лог «message sent to DLQ» | PagerDuty + support |
| Нет логов | `count_over_time` = 0 за 5 мин | Инстанс упал |
| Stuck order | Нет INFO смены статуса > 48 ч | Support (дублирует Task3 monitor) |

### Аномалии

| Паттерн | Детекция | Интерпретация |
|---------|----------|---------------|
| Всплеск создания заказов | 4 → 10 000/сек | DDoS или баг B2B-партнёра → rate limit |
| Рост ERROR без роста RPS | ERROR rate ↑, RPS stable | Баг после деплоя |
| Рост `duration_ms` расчёта | p95 price calc ↑ | Перегрузка MES |

Реализация: Grafana Loki LogQL + recording rules → Prometheus → Alertmanager.


## Выбор технологии (доп. задание)

**Выбор: Grafana Loki** — единый стек с Tempo/Prometheus из Task2–3, низкая стоимость, labels вместо full-text индекса.

| Критерий | ELK (Elastic) | OpenSearch | Splunk | **Loki + Grafana** |
|----------|---------------|------------|--------|---------------------|
| Лицензия | Elastic License | Apache 2.0 | Проприетарная | AGPL / Apache 2.0 |
| Стоимость (self-hosted) | Средняя–высокая (RAM на индексы) | Средняя | Очень высокая | **Низкая** (S3 backend) |
| Интеграция с Tempo/OTel | Плагины, настройка | Аналогично ELK | Хорошая, но $$ | **Нативная** в Grafana |
| Порог входа для команды | Высокий (8 инженеров — тяжело) | Высокий | Высокий + обучение | **Низкий** (уже Grafana) |
| Поиск по order_id | Full-text, быстро | Full-text | Отлично | **Label + JSON filter** — достаточно |
| Нагрузка на инфраструктуру | JVM, много RAM | JVM, много RAM | Отдельный кластер | **Легче** — индекс только labels |
| Yandex Cloud | EC2 self-hosted | EC2 self-hosted | SaaS / VM | **EC2 + S3** (Object Storage) |

**Почему не ELK/OpenSearch:** для 3 API и ~15 GB/мес — overkill; JVM-кластер дорог в поддержке для команды из 8 человек.

**Почему не Splunk:** лицензия несопоставима с бюджетом «Александрита».

**Yandex Cloud Logging** — хорошая альтернатива, если не хотят self-hosted; минус — слабее связка с Grafana Tempo. Компромисс: Loki self-hosted + Yandex S3 как backend.
